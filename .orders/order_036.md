# `.orders/order_036.md`

# 実験5c（ex0051拡張）：学習率・バッチサイズを変えた崩壊対策グリッド

## 1. 目的

ex0051（`report_035.md`）は，バッチサイズ128・学習率0.001・128エポックという設定で，
ASAI SVRGがSeed 3でエポック117付近から近似誤差の急増を伴う崩壊を示すことを発見した．
これは，`report_026.md`（ex0023）がCIFAR-10・バッチサイズ32で報告した「短期的には安定に
見えて長期的に崩壊する」パターンが，これまで最も安定と考えられてきたImagewoof・バッチ
サイズ128・ASAI SVRGという組み合わせでも（低頻度ながら）生じうることを示す，重要な
発見であった．

本実験は，この崩壊への対策として，**ASAI SVRG論文のアルゴリズム自体（Algorithm 3, 4）を
変更しない範囲**で対処可能な2つのハイパーパラメータ変更——(1) 学習率を一桁下げる，
(2) バッチサイズを拡大する——を検証する．勾配クリッピングや内部ループ長の上限設定等，
アルゴリズム自体に手を加える対策は，これまでのプロジェクト全体の方針（理論的に対応する
更新則を保ったまま検証すること）から外れるため対象外とする．

学習率・バッチサイズはいずれも，実験0〜ex0023を通じて最も一貫して不安定性との関連が
確認されてきた変数であり（`report_032_ex002.md` 4.2節等），既存のハイパーパラメータ
グリッドの延長として位置づけられる，恣意性の低い変更である．

## 2. 実験系列の位置づけと実装方針

`programs/ex0051_imagewoof_resnet18_bs128_longrun/` を，単一条件（バッチサイズ128・
学習率0.001）専用のスクリプトから，**グリッド対応**に編集する形で実装すること．新規
ディレクトリは作成せず，`ex0051`のディレクトリ・出力先を拡張する．既存のバッチサイズ128・
学習率0.001・128エポックの20条件（`outputs/ex0051_imagewoof_resnet18_bs128_longrun/`）は
変更せずそのまま保持し，新たな2条件（後述）を追加すること．

`data.py`・`model.py`はex0051から変更しない．`train.py`のタスク生成部分（現在は単一の
ハイパーパラメータの組のみを生成している想定）を，複数のハイパーパラメータの組を生成
できるよう修正すること．

## 3. 実験条件

ex0051の基準条件（バッチサイズ128，学習率0.001，128エポック，$K=71$，総イテレーション
数$128\times71=9088$）に対し，以下の2条件を追加する．

### 条件A：学習率を一桁下げる
- バッチサイズ：128（基準条件と同一）
- 学習率：0.0001（基準条件の1/10）
- $K=71$（バッチサイズ不変のため同一）

### 条件B：バッチサイズを拡大する
- バッチサイズ：512
- 学習率：0.001（基準条件と同一）
- $K=\lceil N_{\text{train}}/512\rceil$（Imagewoofの$N_{\text{train}}=9025$より，
  $K=18$．実装時に正確な値を算出すること）

### 4. エポック数の決定：総イテレーション数を揃える

基準条件（バッチサイズ128，128エポック，$K=71$）の総イテレーション数
$128\times71=9088$に，条件A・Bのエポック数を揃える．

- **条件A**（バッチサイズ128，$K=71$）：学習率のみが変わり$K$は不変のため，
  基準条件と同一の**128エポック**とする
- **条件B**（バッチサイズ512，$K=18$）：総イテレーション数を9088に揃えるため，
  エポック数は $\lceil 9088/18\rceil = 505$ エポック程度となる．実装時に正確な値を
  算出し，端数の扱い（総イテレーション数が基準条件からどの程度ずれるか）をレポートに
  明記すること

- **比較手法**：SGD, SVRG, NFG SVRG, ASAI SVRGの4手法（ex0051と同一）
- **Seed数**：5（0〜4，ex0051と同一．特にSeed 3でex0051と同様の崩壊が再現するかを
  重点的に確認する）
- **正則化係数**：$\lambda=5\times10^{-4}$（ex0051と同一）

条件数は2条件（A, B）×手法4種×Seed5 = 40条件を新規に学習する．

## 4. 実験終了の基準

以下を確認した時点で本実験を完了とする．

1. 条件A・Bともに全20条件が完了し，発散（NaN）の有無を確認すること
2. **崩壊対策としての効果**：条件A（学習率を下げる）・条件B（バッチサイズを拡大する）
   のそれぞれについて，ASAI SVRGのSeed 3（およびその他のSeed）で，基準条件
   （ex0051，`report_035.md` 6.1節）と同様の終盤崩壊が生じるか，あるいは回避される
   かを確認すること
3. ex0051で実装した3指標（隣接相対変化，正味変化量，線形回帰の相対傾き，
   `report_035.md` 2.3節）によるプラトー判定を条件A・Bにも適用し，同一の総
   イテレーション数のもとで基準条件と比べて収束の進み方がどう変わるかを確認すること
4. オラクル呼び出し回数ベースでのASAI SVRGのSVRGに対する優位性（`report_035.md`
   6.4節と同様の比較）が，条件A・Bでも維持されるかを確認すること
5. 崩壊対策として学習率を下げること・バッチサイズを上げることのどちらがより有効か，
   あるいはいずれも崩壊を防げないかについて結論を得ること

## 追記1．実行前見積もりを踏まえた実行方針の変更（チャットでのユーザー指示）

実装後の計算コスト見積もり（6節）の結果，条件B（バッチサイズ512，$K=18$，505エポック）は
VRAM使用量がバッチサイズ128の約3.8倍（約22.6GB vs 約5.9GB，reservedベース）に達すること
が判明した．8プロセス並列のままではVRAM総量（約102.6GB）を大幅に超過するため，条件Bは
4プロセス並列に制限する必要があり，その結果，条件Bのみで推定所要時間が約80〜85時間に
達することが分かった．条件A・基準条件（バッチサイズ128フェーズ，8プロセス並列）と合わせると
全体で4日以上を要する見込みとなった．

この見積もりをユーザーに提示したところ，以下の指示を受けた．

- **まず条件B（バッチサイズを上げて総イテレーション数を揃えた条件）のみを単独で実行する**．
  条件A（バッチサイズ128・学習率0.0001）は本実行の対象から外し，別途後日実行する
- 上記の方針を本オーダーに追記すること（本追記）
- 条件Bの実行完了後，条件Aを追加実行できるよう，実装上の準備をしておくこと

この指示に基づき，`programs/ex0051_imagewoof_resnet18_bs128_longrun/train.py`の`main`関数を，
バッチサイズ128フェーズ（基準条件・条件A，`run_bs128_phase`関数）とバッチサイズ512フェーズ
（条件B，`run_bs512_phase`関数）を独立に実行できるよう`run_bs128`・`run_bs512`引数を持つ
形に変更し，`if __name__ == "__main__":`のブロックでは`main(run_bs128=False,
run_bs512=True)`として条件Bのみを実行するようにした．条件Aを追加実行する際は，同ブロックを
`main(run_bs128=True, run_bs512=False)`（または引数なしの`main()`）に変更して再実行すれば
よく，条件B（学習済み）は`is_run_completed`により自動的にスキップされ，条件Aのみが新規に
学習される．詳細は`.reports/report_036.md`を参照．
